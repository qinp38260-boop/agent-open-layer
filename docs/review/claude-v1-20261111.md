## 原文

先说明：我只能审你的文字和推理，没看到代码、日志、测试用例。下面标【实测】的，指"你的描述若属实，该事实成立"，不是我复现过。

1. 致命问题
1.1 “L0 全部实跑”与"账号已停用"并存，对外必须只写后者。【推断】
14+4 项验收只证明"该账号启用时的状态"。停用后，没有任何主体隔离在生效，当前态就是 config-only。文档里不能出现"已实现独立工位隔离"的现在时措辞。

1.2 hook fail-open 是致命项，不是"已知限制"。【实测，按你的 6/6】
闸门本身可被异常绕过，意味着它不是闸门，是"正常路径下的提示"。任何"越界时被拦下"的表述都要加前提：hook 正常运行、未被 agent 自己触发异常。更要问的是：agent 能否主动制造 hook 异常？（超长输入、畸形 JSON、非 UTF-8 路径、让 hook 超时。）若能，一次尝试就绕过，这比 4 个路径绕过严重得多。

1.3 L2 的结论范围过大。【推断】
蜜标 0 请求证明的是：这一次、这个 agent 的内置工具通道没有发起 HTTP 到该蜜标地址。它没证明 shell 工具、git、pip、DNS 解析、非 HTTP 协议（ping/raw socket）也被封。若你写"网络已隔离"，不成立；只能写"受限档下，探针所覆盖的出站路径未观察到外联"。

2. 重要问题
A. 阴性对照的推理链【推断】
"放开档命中=探针有效"只证明探针能检测到某一条出站路径，不证明它覆盖了受限档下所有路径。这是"对照有效性"和"覆盖完备性"的混淆。另外，蜜标在本机，若受限档只是拦了"访问外网"而放行 localhost，你测的可能是另一回事，请确认受限档下 localhost 本身是否可达，否则 0 请求可能是 agent 没尝试，而非被拦。也要说明模型是否真的被诱导去访问蜜标（DeepSeek 可能根本不会照做）。建议证据等级再加一档：probe-verified-narrow（仅覆盖已测路径）。

B. 同类路径绕过（具体攻击式）【推断，均未验证，需你逐条复现】

8.3 短名：D:\AGENT~1\.. 与长名归一化不一致。
大小写与 Unicode 归一：D:/AGENT-WORK 通过白名单比较；全角字符、％ 编码。
保留设备名：D:/agent-work/CON、NUL、aux.txt。
硬链接：根内 mklink /H D:\agent-work\x C:\Windows\... 在权限足够时无需管理员，与 junction 同类，realpath 折祖先管不到。
符号链接/目录 junction 的 TOCTOU：闸门检查时是合法目录，执行前被替换。
UNC 与映射盘：\\localhost\D$\...、\\?\UNC\、subst/net use 造出的新盘符。
相对路径依赖 cwd：命令先 cd 再用相对路径，或 PowerShell 变量/$env: 拼接，闸门只做静态解析。
间接写入：git -C、robocopy、xcopy、tar -C、python -c "open(...)"，目标不在命令行显式字段里。
重命名/移动：源在根内、目标在根外（Move-Item、rename）。
ADS 变体：file.txt::$DATA、:stream，你只说了"去 ADS"，请测 ::$DATA 与目录 ADS。
C. L0/L2 的诚实结论
"警示装置，不是安全边界"不是过于谦虚，基本准确，但需拆开：L0 启用时是真实的 OS 级主体隔离（ACL 由内核执行），这是安全边界级别的东西，只是不是对抗强攻击者的完整边界（无沙箱、无网络隔离）。把它和 hook 层一起笼统说"警示装置"会低估 L0、高估 hook。建议分层表述。

3. 建议的 3 处修改
修改 1（总纲声明，放 README 第一屏）：

"本项目在无管理员权限的 Windows 上，提供意图级的越界拦截与取证。它不是安全沙箱：hook 异常时可能放行（实测 6/6），拆分命令可绕过，网络隔离仅经蜜标在已测路径上验证。请勿用于隔离不可信或有对抗意图的 agent。"

修改 2（证据等级表加当前态列）：

“L0 独立账号：验收 14+4 项通过（账号启用时）｜当前状态：账号已停用，未生效。”

修改 3（给实施工程师的结论）：

"装好后，agent 在正常情况下会被拦在 D:/agent-work 内并留下记录；这不等于它无法越界。出现拦截记录说明在起作用，没有记录不能说明没有越界。重要数据请不要放在 agent 能访问的机器上。"

D. 最易被误读的一条
"网络受限档：蜜标收到 0 个请求"。非专业人士会读成"断网了"。改写为"在我们测的那条路径上没发现外联"。

E. 发布前最该补的一件事
把 hook 的 fail-open 改成 fail-closed，或至少证明 agent 无法触发它。【推断】其余都是文档措辞可补救的，这条是设计层的根本漏洞。附带：公开一份对抗用例清单与复现脚本，让别人能独立验证你的 7/7 与 141 条。

不确定之处
你的"意图×目标"判定细节、141 条覆盖范围，我看不到。
“fail-open 实测 6/6"是哪 6 种触发方式？是宿主配置层面可修，还是 Codex 本身行为？表述含糊，请明确。
判决
